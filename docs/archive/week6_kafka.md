# 6회차 — 부하 테스트와 장애 대응

## 1. 목표와 테스트 범위

**목표: 초당 100건을 지연 p95 30초 이내로 저장하고, 입력 중단 후 Kafka lag를 0으로 회복한다.**

실시간 운영과 같은 `write_audit` 저장 코드를 사용한다. 경로는 Kafka → Spark 검증 → executor JDBC staging → PostgreSQL 일괄 병합이다. Airflow 일일 집계와 Parquet snapshot 생성 시간은 이번 실시간 적재 측정에서 제외한다.

테스트는 별도 `week6-*` 토픽·DB·checkpoint를 사용한다. 원본 샘플의 구조는 유지하되 event_id를 매번 새로 생성하여 중복 제거 때문에 처리 건수가 줄어들지 않게 했다. 공개 Wikimedia API에 부하를 보내지 않는다.

## 2. 부하 시나리오

| 단계 | 목표 입력 속도 | 유지 시간 |
|---|---:|---:|
| 1 | 100건/초 | 3분 |
| 2 | 300건/초 | 3분 |
| 3 | 1,000건/초 | 3분 |
| 4 | 3,000건/초 | 3분 |
| 장애 주입 | 1,000건/초, 절반은 깨진 JSON | 10초 |
| 장애 이후 | 정상 100건/초 | 10초 |

각 단계 사이에 backlog를 비우지 않고 입력을 연속해서 늘린다. 마지막에는 입력을 중단하고 backlog가 사라질 때까지 기다린다. 순간 폭증·30분 soak는 선택 항목이므로 이번에는 실행하지 않는다.

조건: Spark `local[2]`, driver 메모리 1GB, trigger 10초, `maxOffsetsPerTrigger=20,000`, JDBC 병렬 연결 4개, Kafka 3 partitions. 같은 Docker 환경에서 실제 수집 서비스도 동작한다. 자세한 자원 설정과 측정은 결과 폴더의 `host.json`, `environment.json`, `resources.jsonl`에 저장한다.

## 3. 지표를 계산하는 방법

| 지표 | 측정 방식 |
|---|---|
| 실제 입력 속도 | 생성기가 Kafka 큐에 넣은 수 / 단계 경과 시간. 마지막에 전달 성공 건수를 별도로 대조 |
| 저장 완료 처리량 | 해당 시간 구간에서 완료한 배치 입력 수 / 단계 경과 시간. 정상·오류 저장을 모두 포함 |
| Spark 처리 속도 | lastProgress의 inputRowsPerSecond·processedRowsPerSecond 원본 보관 |
| 배치 시간 | lastProgress.durationMs.triggerExecution |
| Kafka lag | 브로커에서 직접 조회한 최신 offset − 마지막 완료 배치 endOffset, partition별 합계 |
| 지연 p50·p95 | 단계 중 생성한 정상 메시지의 processed_at − ingest_time, 전부 처리한 뒤 계산 |

리플레이의 원래 event_time은 과거 시각이다. 전송 직전에 갱신하는 **ingest_time을 produced_at 역할**로 사용한다. processed_at은 DB 삽입 트랜잭션의 시각이므로 엄밀한 커밋 완료 지연보다 짧을 수 있다.

Spark의 processedRowsPerSecond는 배치가 실제 처리되는 동안의 속도다. 10초 주기의 대기 시간까지 포함한 저장 완료 처리량과 같지 않다. lag는 10초 간격 표본이므로 순간 최대치 전체를 포착하지 못할 수 있다.

## 4. 장애 대응

깨진 JSON을 정상 메시지와 섞어서 대량으로 넣는다. 정상 데이터는 `week4.edits`, 잘못된 메시지는 `week4.rejected`로 분리한다. 이후 정상 메시지를 추가해 처리가 계속되는지 확인한다.

검증 기준:

- 전달 성공 수 = 정상 테이블 수 + 오류 테이블 수.
- 오류 테이블 수 = 의도적으로 깨뜨린 메시지 수.
- 오류 주입 이후 보낸 정상 메시지도 전부 저장.
- 마지막 Kafka lag = 0.

지연 p95 30초 또는 lag 10,000건을 넘으면 `stream/alerts.jsonl`에 기록한다. 외부 알림 발송은 설정하지 않았다. Spark 프로세스가 실패하면 운영 서비스는 컨테이너를 재시작하고 기존 checkpoint에서 이어간다. 이번 직접 장애 실험은 서비스 중단이 아니라 **깨진 메시지 폭증**이다.

## 5. 측정 결과

| 입력 속도 | 저장 완료 속도 | 배치 시간 중앙값 | 지연 p95 | lag 처음 → 마지막 | 판단 |
|---:|---:|---:|---:|---:|---|
| 100건/s | 96.6건/s | 0.81초 | 10.34초 | 349 → 429 | 지연 안정 |
| 300건/s | 293.2건/s | 0.95초 | 10.38초 | 1,310 → 1,744 | 지연 안정 |
| 1,000건/s | 976.2건/s | 1.41초 | 10.77초 | 5,932 → 7,556 | 지연 안정 |
| 3,000건/s | 1,987.3건/s | 2.22초 | 89.96초 | 11,313 → 176,940 | 입력 제한으로 backlog 증가 |

**먼저 막힌 곳: DB 처리 자체가 아니라 `maxOffsetsPerTrigger=20,000`과 10초 trigger의 조합이다.** 약 2,000건/초까지만 새 배치에 받아들이는데 3,000건/초가 들어와 lag가 늘었다. 실제 배치 시간은 약 2.22초로 10초보다 짧았다. 이 관찰만으로 DB의 최대 처리 한계를 측정했다고 볼 수는 없다.

100~1,000건/초에서도 표의 저장 완료 속도가 입력보다 조금 낮게 나오는 것은 단계 경계에 걸친 마지막 배치가 다음 구간에서 끝나기 때문이다. 각 단계의 입력을 전부 처리한 후 건수를 대조했으며 누락은 없었다. lag의 시작·끝 표본만으로 장기 증가 추세를 단정하지 않고 배치 시간과 전체 시계열을 함께 봤다.

- 총 803,000건 전달 성공 → 정상 798,000건 + 오류 5,000건.
- 깨진 메시지 5,000건 모두 오류 테이블에 보존.
- 장애 주입 이후 정상 1,000건도 모두 저장.
- 입력 종료 후 마지막 lag 0 확인. 로컬 임계치 알림 28회 기록.
- 첫 100건/초 단계의 지연 p95는 10.34초로 목표 30초 이내를 충족했다.

## 개선 전후 비교

배치 제한은 20,000건으로 유지하고, trigger를 10초에서 5초로 줄여 초당 3,000건을 다시 3분간 입력한다. 한 번에 읽는 크기를 키우지 않고 실행 간격만 줄이는 방법이다. 두 실행은 동시에 돌리지 않았다. 별도 새 DB에서 각 한 번씩 실행했으므로 통계적으로 보장된 최대 처리량은 아니다.

```bash
python3 scripts/week6.py --rates 3000 --trigger 5
```

| 초당 3,000건 비교 | 기존: 10초 주기 | 개선: 5초 주기 |
|---|---:|---:|
| 배치당 입력 한도 | 20,000건 | 20,000건 |
| 저장 완료 속도 | 1,987.3건/s | 2,945.3건/s |
| 배치 시간 중앙값 | 2.22초 | 1.93초 |
| 지연 p95 | 89.96초 | 6.18초 |
| 단계 마지막 lag 표본 | 176,940건 | 13,818건 |
| 전체 입력 종료 후 lag 0 관측까지 | 79.25초 | 13.35초 |

**배치 주기를 줄이자 지연 p95가 약 90초에서 6.18초로 줄었다.** 개선 실행에서도 정상 546,000건 + 오류 5,000건 = 전달 551,000건이 일치했고, 최종 lag는 0이었다. 운영 Spark에도 5초 trigger를 적용한다.

lag 회복 시간은 10초 간격 관측값 기준이다. 개선 후에도 주기 사이에 메시지가 쌓이므로 lag가 항상 0인 것은 아니다. 고정 lag 10,000건 임계치로 개선 실행에서도 알림 9회가 발생했다. 높은 입력 속도에서는 정상 주기 대기량도 임계치를 넘을 수 있으므로 지연 p95와 함께 판단하고 알림 기준을 조정해야 한다.

## 재현과 파일 위치

운영 환경을 먼저 시작한 후 실행한다.

```bash
python3 scripts/operations.py start --legacy-streaming
python3 scripts/week6.py
```

간단한 실행 확인만 하려면 `python3 scripts/week6.py --seconds 10 --rates 100,300`을 사용한다. 이 짧은 실행은 과제의 3분 유지 본 실험을 대체하지 않는다.

- `src/load_generator.py`: 속도 제어·고유 ID·전송 성공 확인
- `src/monitored_stream.py`: 운영과 테스트에서 공통으로 쓰는 적재·모니터링
- `scripts/week6.py`: 격리 환경 생성·부하 실행·backlog 회복 대기
- `scripts/report_week6.py`: 전체 입력 대조·지표 계산·표 생성
- `evidence/week6/<실행 ID>/`: producer.json, report.json, summary.md, stream 지표와 로그
- `artifacts/live/stream/`: 운영 데이터의 지표와 checkpoint

부하 테스트 DB는 운영 DB와 분리해 보존한다. 테스트 checkpoint는 로컬 artifacts에 보관하고, 제출용 지표·요약·압축 로그는 evidence에 둔다. 예비 실행 결과는 artifacts/week6/preflight에 보관한다.
