# 3주차 과제 — Wikipedia 편집 기록을 Kafka로 보내기

## 데이터 출처와 10분 수집 규모

데이터는 [Wikimedia EventStreams의 recentchange API](https://stream.wikimedia.org/v2/stream/recentchange)에서 수집했다. 이 API는 위키미디어 서비스에서 발생하는 편집·문서 생성 등의 변경 기록을 JSON 형태로 계속 보내준다. 한 번 연결하면 새 데이터를 이어서 받는 **SSE 방식**이다.

2026년 10월 25일 **19:04:23~19:14:23(한국시간)**에 10분간 수집했다.

| 측정 항목 | 결과 |
|---|---:|
| 전체 Wikimedia 변경 기록 | 25,860건 |
| 전체 기록의 평균 수신 속도 | 약 43.10건/초 |
| 전체 JSONL 파일 크기 | 36.80MB |
| gzip으로 압축한 파일 크기 | 5.17MB |
| Wikipedia 편집 기록만 선택 | **3,846건** |
| 선택한 편집 기록의 평균 수신 속도 | 약 6.41건/초 |

JSONL은 JSON 기록을 한 줄에 하나씩 저장한 파일이다. MB는 1,000,000바이트 기준이다. 이 수치는 **해당 10분 동안 수신한 데이터**를 기준으로 측정했다.

전체 데이터에는 Wikipedia 외에도 Wikidata·Commons 등의 기록이 들어 있다. 이번 과제에서는 **사이트가 `.wikipedia.org`로 끝나고, 변경 유형이 `edit`인 기록**만 골랐다. 선택된 3,846건을 파일에서 다시 읽어 Kafka로 전송하고, 제대로 도착했는지 확인했다.

## 1. Producer 코드 흐름

코드: [src/producer.py](src/producer.py)

```text
수집 파일 읽기 → 위키피디아 편집만 선택 → JSON 메시지 만들기
→ Kafka로 전송 → 콜백으로 성공·실패 확인 → Consumer로 읽기
```

**Producer**는 데이터를 Kafka에 보내는 프로그램이고, **Consumer**는 Kafka에 저장된 데이터를 읽는 프로그램이다. 이번 Producer는 다음 순서로 동작한다.

1. **데이터 읽기:** 수집한 JSONL 파일을 한 줄씩 읽고, Wikipedia 편집 기록만 선택한다.
2. **메시지 만들기:** 원본 데이터에 식별자·발생 시각·형식 버전 등의 공통 필드를 붙인다. 같은 실행에서 이미 읽은 식별자는 중복 전송하지 않는다.
3. **직렬화와 전송:** 메시지를 JSON 문자열과 UTF-8 바이트로 바꾼다. 이를 **직렬화**라고 하며, `produce()`로 key와 메시지를 Kafka에 보낸다.
4. **결과 확인:** 전송 결과를 알려주는 **콜백**에서 성공하면 파티션과 offset(저장 위치)을 기록한다. 실패하면 오류와 해당 메시지를 파일에 남긴다.
5. **남은 전송 마무리:** `poll()`로 콜백을 처리하고, 종료할 때 `flush()`로 아직 전송 중인 메시지가 끝나기를 기다린다.

일시적인 전송 오류는 Kafka 클라이언트가 최대 120초 동안 재시도한다. `enable.idempotence=true`로 내부 재시도에 따른 중복을 줄이고, `acks=all`로 저장 확인 응답을 받는다. 다만 프로그램을 새로 실행해 같은 파일을 다시 보내는 경우까지 중복을 막아주는 것은 아니다.

## 2. 실제 전송한 메시지

**key:** `enwiki:Bey` — 영어 위키피디아의 `Bey` 문서를 뜻한다.

아래는 실제로 전송하고 읽은 JSON이다. 길이를 줄이기 위해 `payload`의 일부 필드만 표시했다. [전체 메시지 원문](evidence/submission_message.json)

```json
{
  "event_id": "5b91f22d-50ac-476e-93be-97203972b30c",
  "event_type": "wikipedia.edit",
  "event_time": "2026-10-25T10:10:12+00:00",
  "ingest_time": "2026-10-25T10:28:04.414157+00:00",
  "schema_version": 1,
  "source": "wikimedia-recentchange-replay",
  "payload": {
    "wiki": "enwiki",
    "title": "Bey",
    "type": "edit",
    "bot": false
  }
}
```

메시지는 **편집 데이터를 설명하는 공통 필드**와 **원본 데이터인 payload**로 구성했다.

| 필드 | 의미와 사용 목적 |
|---|---|
| `event_id` | 편집 기록의 고유 식별자. 같은 기록인지 확인하고 중복을 처리할 때 사용한다. |
| `event_type` | 어떤 종류의 데이터인지 나타낸다. 이번에는 `wikipedia.edit`이다. |
| `event_time` | 원래 편집이 발생한 시각. 나중에 시간대별 편집량을 집계할 때 사용한다. |
| `ingest_time` | Producer가 이번 전송 직전에 기록한 시각이다. |
| `schema_version` | 메시지 형식의 버전. 이후 필드가 달라졌을 때 형식을 구분한다. |
| `source` | 데이터가 어디에서 왔는지 표시한다. `replay`는 저장한 데이터를 다시 보냈다는 뜻이다. |
| `payload` | 원래 편집 기록. 위키 이름, 문서명, 봇 여부 등의 정보가 들어간다. |

**key는 JSON 본문과 별도로 전송한다.** `enwiki:Bey`처럼 위키 이름과 문서명을 묶어, 같은 문서의 편집이 같은 파티션으로 가도록 했다. 위 예시의 두 시각이 다른 이유는 수집한 파일을 나중에 다시 전송했기 때문이다. 원래 편집 시각은 변경하지 않았다.

## 3. Topic 구성과 이유

**Topic(토픽)**은 Kafka에서 같은 종류의 데이터를 모아두는 공간이다. **Partition(파티션)**은 그 토픽을 나눈 저장 단위로, 데이터를 여러 작업으로 나눠 읽을 때 사용한다.

| 항목 | 설정 | 선택 이유 |
|---|---|---|
| 토픽명 | `wikipedia-edits` | 위키피디아 편집 기록을 한곳에 모으기 위해 |
| 파티션 수 | 3개 | 데이터를 나눠 처리하는 실습과 이후 부하 테스트를 위해 |
| 메시지 key | `wiki:문서명` | 같은 위키의 같은 문서 편집을 같은 파티션에 보내기 위해 |
| 리텐션(보관 기간) | 7일 | 일주일 동안 데이터를 다시 읽고 실험할 수 있도록 |

Wikipedia 편집은 같은 형식으로 처리하므로 언어별로 토픽을 나누지 않고 하나로 모았다. 파티션 3개는 현재 수신량에 반드시 필요한 수라기보다, 이후 여러 Consumer로 나눠 처리하는 실습을 위한 시작값이다.

같은 key는 같은 파티션에 저장되므로 같은 문서의 기록을 **Kafka에 기록된 순서**대로 읽을 수 있다. 전체 문서 사이의 순서나 편집 발생 시각순 정렬까지 보장하는 것은 아니다.

리텐션을 7일로 정해 처리 프로그램을 수정한 뒤에도 최근 데이터를 다시 읽을 수 있도록 했다. 로컬에서는 Kafka 서버인 **브로커 1개**를 사용하므로, 서버 장애에 대비한 복제 구성은 이번 실습에 포함하지 않았다.

## 실행 확인과 속도 조절

Kafka를 로컬에서 실행하고 토픽을 만든 뒤, `--rate 200`으로 초당 약 200건씩 전송했다.

| 확인 항목 | 결과 |
|---|---:|
| 전송 성공 | 3,846건 |
| 콘솔 Consumer 수신 | 3,846건 |
| 이번 실행의 중복·누락 | 0건 |

[전송 결과](evidence/producer_summary.json) · [콘솔 수신 캡처](evidence/consumer_sample.txt) · [원본 대조 결과](evidence/verification.json)

**보너스:** `--rate` 값으로 초당 전송 건수를 조절할 수 있다. 예를 들어 아래 명령은 샘플 데이터를 초당 10건씩 보낸다. 프로젝트 최상위 폴더에서 Kafka 실행과 Python 환경 준비 후 사용한다.

```bash
python -m src.producer --input samples/wikipedia_edits.jsonl --rate 10
```

환경 설치와 Kafka·토픽 생성 명령은 [기존 상세 README](docs/README_DETAILED.md)의 **5. 재현 방법**에 보관했다.
